2. COMPROBAR EL CÓDIGO — PC CON PYTHON 3.12 Y NODE 24
Instalar Python y Node desde python.org y nodejs.org; Git desde git-scm.com.
En Ubuntu instalar también python3-venv. Confirmar python3 --version y node --version.
  python3 -m venv .venv
  .venv/bin/pip install -r backend/requirements.txt pytest httpx
  cd backend
  ../.venv/bin/python -m pytest -q
  cd ../frontend
  npm ci
  npm run build -- --configuration production
  cd ..
Esperado: 11 pruebas aprobadas y compilación terminada sin errores.
En Windows usar .venv\Scripts\python y .venv\Scripts\pip.
Esto no necesita MySQL; las pruebas sustituyen la DB con datos controlados.
Para desarrollo: desde frontend ejecutar npm start; requiere API local en
127.0.0.1:8000. /api/** se reenvía al backend quitando /api.

3. CREAR Y PREPARAR LOS CUATRO NODOS — EN CADA VM
Usar Ubuntu 24.04: sg-<apellido>-db, -backend, -frontend y -security.
Security debe estar LOCAL con al menos 8 GB; reservar memoria extra para
SonarQube o ponerlo en un PC, posibilidad admitida por el HTML.
  sudo apt update
  sudo apt upgrade -y
  sudo apt install -y openssh-server unattended-upgrades git curl nftables python3 rsyslog
  sudo dpkg-reconfigure -plow unattended-upgrades
Crear un administrador sin ser root; instalar su llave SSH. En sshd configurar
PermitRootLogin no, PasswordAuthentication no y KbdInteractiveAuthentication no.
Validar con sudo sshd -t, recargar ssh y probar otra sesión antes de cerrar la
consola. Verificar valores efectivos con sudo sshd -T; revisar posibles
archivos de cloud-init que tengan precedencia. Crear /opt/examen/grupo.txt con
el código auténtico en los cuatro nodos y mostrarlo junto al hostname.

4. UNIR TAILSCALE Y LIMITAR LA RED — VMs Y TODOS LOS PCs
Instalar desde https://tailscale.com/download y unir todo a la misma tailnet.
Usar claves de alta de un solo uso para servidores y tags db/backend/frontend/security.
Hacer visible GRUPO_CODIGO en el nombre de tailnet o etiqueta, como pide el HTML.
Anotar tailscale ip -4. Completar infra/tailscale-acl.hujson y aplicar en el
panel, retirando la regla general de permitir todo. Identificar cada PC miembro.
Completar red.private.json a partir de infra/network.example.json.
Aplicar por rol el firewall de infra/OPERACION.md desde la consola de cada VM.
El generador no cambia el firewall por sí solo; revisar primero con nft -c.
Flujos TCP autorizados:
- frontend -> backend: APP_PORT; backend -> db: DB_PORT.
- tres nodos y PCs -> security: 1514/1515.
- PCs -> cuatro nodos: 22; PCs -> security: 443/9000; PCs -> backend: APP_PORT.
El navegador público llega al frontend por Cloudflare, sin puerto de entrada público.
Probar nc -vz IP PUERTO desde origen permitido y nc -vz -w 3 IP PUERTO desde
origen no permitido; en Windows usar Test-NetConnection. Guardar ambas salidas.
Configurar la espera de IP Tailscale al iniciar MySQL/Docker según el anexo.

5. INSTALAR MYSQL Y RESPALDO — sg-db
  sudo apt install -y mysql-server age openssl
Seguir infra/OPERACION.md: crear TLS con infra/db/create-tls.sh, completar
mysqld.cnf.template y crear tablas con infra/db/mesa_ayuda.sql.
Aplicar grants.mysql.template.sql en una copia privada: app_mesa@IP_BACKEND,
clave nueva, caching_sha2_password, REQUIRE SSL y solo permisos de datos.
Comprobar: raíz local, puerto asignado, bind en IP Tailscale, TLS verificado,
fallos de autenticación en error.log y general_log OFF. La conexión sin TLS
y CREATE TABLE con app_mesa deben fallar. Registrar SHOW GRANTS sin claves.
Programar mesa-backup.timer, ejecutar un respaldo y descifrar/restaurar en
una base temporal: comparar filas. El anexo contiene comandos y permisos.
Si existen cuentas MD5, ampliar columna con migrate-passwords.sql y luego
restablecerlas desde el backend; conservar usuarios y tickets existentes.

6. DESPLEGAR FASTAPI — sg-backend
Instalar Docker Engine y Compose (en Ubuntu: docker.io y docker-compose-v2).
Comprobar docker --version y docker compose version. Si el usuario no tiene
permiso del daemon, anteponer sudo a docker. Clonar la rama acevedo en esta VM.
  cp backend/.env.example backend/.env
  chmod 600 backend/.env
Editar .env: IPs, puerto asignado, grupo y contraseña DB. Para JWT_SECRET usar
una clave nueva producida por openssl rand -hex 32. No publicar ese resultado.
DB_HOST debe ser la IP_DB incluida en el certificado. TRUSTED_PROXY_IP debe
ser únicamente IP_FRONTEND. Copiar la CA pública a backend/secrets/db-ca.pem
(lectura para el contenedor; nunca copiar la clave privada).
  mkdir -p backend/secrets
  sudo install -d -o 10001 -g 10001 -m 0750 /var/log/mesa_ayuda
  cd backend
  docker compose config --quiet
  docker compose up -d --build
  docker compose ps
Desde un PC autorizado: curl http://IP_BACKEND:APP_PORT/health y /ready.
Ambos deben dar 200, grupo correcto; /ready comprueba además MySQL/TLS.
/health solo comprueba que la API vive. Si /ready da 503, revisar IP/puerto,
CA, permisos app_mesa y firewall. Swagger privado: misma dirección con /docs.
Para usuario MD5: docker compose exec backend python -m app.reset_password USUARIO.

7. DESPLEGAR ANGULAR, NGINX Y HTTPS — sg-frontend
Instalar Docker/Compose, clonar acevedo, copiar frontend/.env.example a .env
con IP_BACKEND y APP_PORT. Desde frontend/:
  docker compose config --quiet
  docker compose up -d --build
  docker compose exec frontend nginx -t
  curl -i http://127.0.0.1:8080/api/ready
Esperado: 200 y cabeceras CSP, nosniff, DENY, Referrer-Policy y Permissions-Policy.
Instalar cloudflared desde https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/
Desde la raíz del repo:
  sudo install -m 644 infra/systemd/cloudflared-mesa.service /etc/systemd/system/
  sudo systemctl daemon-reload
  sudo systemctl enable --now cloudflared-mesa
  sudo journalctl -u cloudflared-mesa --no-pager -n 30
El servicio presupone /usr/bin/cloudflared; comprobar con command -v cloudflared.
Copiar la URL HTTPS trycloudflare.com del log. Cambia al reiniciar el túnel;
es válida para la práctica. Para URL estable, configurar un túnel con nombre.
Comprobar desde Internet: registro, login, crear/buscar/abrir ticket, cerrar
sesión; Network debe usar /api. Revisar que CSP no rompa componentes.
/api/docs y /api/openapi.json deben dar 404; Swagger solo es privado.
Con dos usuarios, el segundo no debe leer ni modificar el ticket del primero.
Una descripción <b>prueba</b> debe verse como texto, sin interpretarse como HTML;
la PoC XSS completa del informe debe demostrar que tampoco se ejecuta script.
Comprobar DevTools: no token en localStorage; recargar exige nuevo login.
